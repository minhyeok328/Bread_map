# Codex 운영 규칙 설계

**작성일:** 2026-07-22
**상태:** 승인됨
**대상 산출물:** 저장소 루트 `AGENTS.md`

## 1. 목적

이 설계는 Codex에서 사용하는 Sol Ultra의 추론 품질과 구현 능력을 제한하지 않으면서, 중복 탐색·과도한 문맥 전달·불필요한 Subagent 생성·반복 검토로 발생하는 토큰 낭비를 줄이기 위한 저장소 운영 규칙을 정의한다. 저장소 루트 `AGENTS.md`가 Bread_map 아래의 Codex 작업에 자동 적용되는 실행 정책을 소유한다.

규칙은 토큰 사용량 자체를 기계적으로 최소화하는 것이 아니라 다음 원칙을 따른다.

- 주 에이전트가 직접 처리할 수 있는 작업은 직접 처리한다.
- 새 스레드와 Subagent는 작업 경계를 명확하게 만들 때만 사용한다.
- 이미 확인한 사실과 변경되지 않은 파일을 이유 없이 다시 조사하지 않는다.
- 검증을 생략해 토큰을 절약하지 않는다.

## 2. 작업 계층

작업 계층은 `Epic → Feature → Task`로 통일한다.

| 계층 | 의미 | 실행 경계 |
|---|---|---|
| Epic | 여러 사용자 결과를 포함하는 큰 목표 | 계획과 Feature 분해를 담당한다. Epic 전체를 한 구현 스레드에서 처리하지 않는다. |
| Feature | 독립적으로 설명하고 검증할 수 있는 사용자 또는 시스템 결과 | Feature마다 새로운 Codex 스레드를 사용한다. |
| Task | Feature를 완성하기 위한 구체적 구현·테스트·문서 작업 | 해당 Feature 스레드에서 주 에이전트가 기본적으로 수행한다. |

새 Feature가 시작될 때 현재 에이전트는 새 스레드 사용을 권고한다. Codex 스레드 생성은 사용자의 명시적 요청이 있을 때만 수행한다. 구현과 직접 검증처럼 밀접하게 연결된 Task는 같은 Feature 스레드에서 끝까지 처리한다.

## 3. Subagent 정책

Subagent는 Task의 기본 실행자가 아니라 제한적으로 선택할 수 있는 위임 수단이다.

### 3.1 기본값과 상한

- 각 Feature 스레드의 기본 Subagent 수는 0개다.
- Feature 스레드당 기본 최대 2개의 Subagent만 생성한다.
- 2개를 초과하려면 사용자의 명시적 승인을 받는다.
- Subagent가 다른 Subagent를 생성하는 재귀 위임은 금지한다.
- 같은 목적의 새 Subagent를 반복 생성하지 말고, 기존 Subagent에 후속 작업을 전달할 수 있으면 재사용한다.

### 3.2 생성 허용 조건

주 에이전트는 다음 조건을 모두 만족할 때 Subagent 사용을 재량으로 결정할 수 있다.

1. Task의 목표와 완료 조건을 짧고 명확하게 설명할 수 있다.
2. 다른 진행 작업과 파일·상태·결정 의존성이 낮다.
3. 결과를 독립적으로 검증하고 주 에이전트가 짧게 통합할 수 있다.
4. 위임 설명과 결과 통합 비용보다 병렬 처리 또는 전문 검토의 이익이 크다.

대표적인 허용 사례는 서로 겹치지 않는 모듈의 구현, 독립된 데이터 조사, 인증·권한·민감정보처럼 범위가 명확한 고위험 검토다.

### 3.3 생성 금지 조건

다음 작업에는 Subagent를 생성하지 않는다.

- 저장소 전체를 막연하게 탐색하는 작업
- 주 에이전트가 짧게 직접 완료할 수 있는 작업
- 앞선 결과가 있어야 시작할 수 있는 순차 Task
- 동일 작업에 대한 중복 구현 또는 중복 전면 리뷰
- 단순 상태 확인, 포맷팅, lint, 단일 테스트 실행
- 작업을 작게 보이게 만들기 위한 인위적인 분할
- 벽시계 시간만 줄고 전체 토큰·통합 비용은 증가하는 병렬화

### 3.4 전달 문맥

Subagent에 전체 대화 기록을 전달하지 않는다. 다음 항목만 포함한 간결한 작업 브리프를 제공한다.

- 목표와 필요한 산출물
- 이미 확정된 결정
- 현재 상태와 남은 작업
- 관련 파일과 필요한 심볼
- 변경 금지 범위와 안전 제약
- 실행할 검증과 완료 조건

주 에이전트는 모든 결과의 최종 검토·통합·사용자 보고를 책임진다.

## 4. 문맥과 탐색 관리

- 현재 Feature와 직접 관련된 최근 대화와 확정된 결정만 유지한다.
- 먼저 파일명·문자열·심볼·오류·호출 지점을 검색해 범위를 좁힌다.
- 관련 파일과 로그 구간만 읽고, 영향 분석이 필요할 때만 범위를 확장한다.
- 변경되지 않은 파일과 이미 확인한 사실은 구체적인 이유 없이 다시 읽거나 조사하지 않는다.
- 새로운 Epic 또는 독립적인 Feature가 시작되면 새 스레드를 권고한다.
- 구현과 검증, 실패 원인 분석과 수정처럼 강하게 연결된 단계는 같은 스레드에서 완료한다.

## 5. 검토와 검증

- 기본적으로 전체 범위 리뷰는 한 번만 수행한다.
- 변경 후에는 수정 영역과 직접 의존성만 다시 검증한다.
- 인증, 권한, 배포, 민감정보, 파괴적 작업, 데이터 손실 위험에는 추가 검증을 허용한다.
- 동일 실패가 반복되면 같은 방법을 재시도하지 말고 근본 원인과 새로운 증거를 재평가한다.
- 합리적인 시도 후에도 해결되지 않으면 증거, 시도한 방법, 현재 차단 요인과 선택지를 사용자에게 보고한다.
- 관련 검증 결과가 확인되기 전에는 완료를 선언하지 않는다.

## 6. 응답 규칙

최종 보고는 다음 항목에 집중한다.

- 달성한 결과
- 중요한 변경
- 수행한 검증과 결과
- 남은 위험 또는 미해결 항목
- 필요한 사용자 결정

전체 작업 과정을 길게 반복하거나, 이미 전달한 조사 내용을 다시 나열하지 않는다. 토큰 절약을 이유로 필요한 분석·안전 확인·검증을 생략하지 않는다.

## 7. `AGENTS.md` 작성 방식

최종 `AGENTS.md`는 Codex 해석의 모호성을 줄이기 위해 영어로 작성한다. 범용 GPT 지침은 포함하지 않는다. 다음 순서를 사용한다.

1. Purpose and Priority
2. Work Hierarchy and Thread Boundaries
3. Subagent Decision Rules
4. Context and Inspection Discipline
5. Review, Verification, and Retry Limits
6. Response Style

제품 요구사항을 `AGENTS.md`에 복제하지 않는다. 제품·기술 기준은 [문서 허브](../../README.md)에서 찾고, `AGENTS.md`는 작업 방식만 소유한다.

## 8. 완료 조건

- `Epic → Feature → Task`의 의미와 경계가 명확하다.
- Feature별 새 스레드 원칙과 사용자 요청 없는 자동 생성 금지가 함께 표현된다.
- Subagent 기본값 0개, 기본 최대 2개, 재귀 위임 금지가 명시된다.
- 허용 조건과 금지 조건이 모두 포함된다.
- 전체 대화 전달 금지와 간결한 브리프 항목이 정의된다.
- 중복 탐색·전면 재검토·무한 재시도 방지 규칙이 포함된다.
- 검증 품질이나 안전을 희생하지 않는다는 원칙이 유지된다.
- 기존 제품 문서와 규범을 중복하거나 변경하지 않는다.
